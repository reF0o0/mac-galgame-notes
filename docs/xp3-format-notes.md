# XP3 / CX 格式笔记

只记本项目实际踩到的部分，不追求覆盖完整的 XP3 规范。

## 头部

```
0x00  11 字节魔数       "XP3\r\n \n\x1a\x8b\x67\x01"
0x0b  u64              第一个索引块的文件偏移
```

注意是 **`0x0b`**。头部后面还有一些字节（例如指向内嵌 PNG 图标的指针），
容易被误当成索引指针 —— 我们一开始就搞错过一次，白查了半天。

## 索引块链

索引可以不止一块。定位规则：

```
seek(0x0b); 读 u64 → 第一块偏移
对每一块：
    flag = 1 字节
        bit0..2 = 编码方式（1 = zlib，0 = 不压缩）
        bit7    = 后面还有下一块
    按编码方式读 size / data
    读完 data 之后的位置就是"下一块的指针"所在处（8 字节 u64）
```

也就是说链的结构是交织的：

```
[头 @0x0b: 指针] [块0 数据] [指针→块1] [块1 数据] [指针→块2] ...
```

每个块的 data 是一串 sub-chunk，本项目只关心两种：

- `info`：`flags(u32) orgsize(u64) arcsize(u64) namelen(u16) name(utf-16le)`
- `segm`：若干个 28 字节的段描述
  （`flags(u32) start(u64) orgsize(u64) arcsize(u64)`）

一个 `File` chunk = 一个条目 = 一对 `info` + `segm`。

## 写入策略：为什么必须"最小改动"

试过的**错误做法**：读索引 → 按原顺序重排所有条目 → 重写整个归档。
结果游戏直接 `失敗。`，进程里看不到它打开这个归档。这类归档的重建一旦有任何
偏移对不上，引擎是全盘拒收的，不给你半点提示。

**正确做法**（`tools/xp3_replace.py`）：

1. 新的条目内容用该条目自己的 `aldr` 过一遍 CX（见下）得到密文；
2. 密文**追加到文件末尾**，数据区一个字节都不移动；
3. 只改这个条目的 `info.orgsize / info.arcsize` 和
   `segm[0].start / orgsize / arcsize`；
4. 把改过的**那一块**索引重新压缩、也追加到文件末尾；
5. 把"指向这一块"的那一个指针改写掉：
   - 如果改的是第 0 块 → 改 `0x0b` 那个指针；
   - 否则 → 改上一块数据末尾的那个指针（`blocks[i-1].after`）。

旧数据和旧索引块留在文件里没人指向，白白占几十 MB，但换来的是**绝不动已经
正确的那些字节**。对游戏引擎来说这是最安全的改法。

## CX 加密

受保护的归档里，条目正文是 CX 加密的。要点：

- 密钥流由条目的 `aldr`（索引里的一项，正好是我们的 CX 派生哈希）决定，
  并且**与位置相关**：`decode` 在 `(aldr & 0x134) + 0x736` 处切成两段，
  第二段用 `(aldr >> 16) ^ aldr` 重新派生。所以可以只解一段前缀来偷看文件头。
- 加密是自反的 XOR 密钥流：**同一个函数既能解密也能加密**。
  写入新内容前必须过一遍，否则引擎再解一次得到的就是噪声。
- 写回时 `aldr` 保持不变 —— 它跟着条目记录走，我们只换正文。

`tools/cxdec.py` 是引擎自身过滤器的忠实移植，两个容易写错的点：

* 归档哈希在 TJS 里是 `tjs_uint32`，也就是**正数**，所有右移都是逻辑右移；
* `shl_reg` / `shr_reg` 这两个 opcode 各自压入 `1+2+3+2+1 = 9` 字节，
  不是 8。

密钥表（`table_ECB` 指令读的那张 1024 项表）没有写进代码，运行时从游戏自带的
`xp3filter.tjs` 里读，用 `--filter` 或 `$XP3FILTER_TJS` 指定。
